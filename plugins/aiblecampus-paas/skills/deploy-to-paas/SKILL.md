# 에이블캠퍼스 PaaS 앱 완성과 배포

사용자가 인프라를 이해하지 않아도 요청한 웹앱을 완성하고 접속 가능한 상태로 만든다. 소스 패키징, 컨테이너, revision과 내부 API는 작업 수단이지 사용자에게 설명할 기본 내용이 아니다.

## 기본 행동

- 사용자가 로컬에서만 작업해 달라고 하지 않았다면 구현과 검증 뒤 배포한다.
- 기존 프로젝트의 구조, package manager, lockfile과 실행 방식을 보존한다.
- 요청한 기능을 빠뜨리지 않고 완성한 뒤 `validate_project`를 통과한 정확한 소스만 배포한다.
- 사용자가 기존 배포를 수정하는 경우 같은 배포 이름을 사용해 접속 주소를 유지한다.
- 배포가 성공하면 URL과 사용 가능한 기능을 먼저 알려준다.
- 브라우저 조작, screenshot과 시각 검사는 사용자가 요청했거나 기능 확인에 꼭 필요한 경우에만 한다. 플랫폼 healthcheck 통과만으로 배포 완료를 판정할 수 있다.

## 사용자와 소통하는 방법

사용자는 비개발자일 수 있다. 진행 상황은 사용자가 이해할 수 있는 단계로 짧게 설명한다.

- 준비: "요청한 기능을 완성하고 있습니다."
- 검증: "완성된 앱이 정상적으로 실행되는지 확인하고 있습니다."
- 배포: "앱이 준비됐습니다. 지금 접속할 수 있게 배포하고 있습니다."

한 단계가 60초보다 오래 걸릴 때만 짧은 추가 진행 상황을 보낸다. 다음 내용은 사용자가 묻거나 직접 조치해야 할 때만 설명한다.

- 소스 압축과 업로드 방식
- 명령어, 파일 경로와 package manager 내부 처리
- 토큰, Credential, 내부 API 주소와 임시 파일
- 배포 ID, revision ID, 컨테이너, 이미지와 대기열 내부 수치

복구 가능한 기술 오류는 먼저 직접 해결한다. 실패한 명령과 긴 로그를 그대로 전달하지 말고, 해결할 수 없을 때만 사용자가 이해할 수 있는 원인과 필요한 다음 행동을 설명한다.

## 실행 경로 선택

### 빠른 배포 경로

다음 조건을 모두 만족하면 `validate_project`와 `deploy_project`만으로 진행한다.

- 프로젝트 구현이 이미 끝났다.
- 사용자가 기능 변경을 요청하지 않았다.
- 필요한 일반 설정과 비밀값이 준비돼 있다.
- DB나 파일 Storage 연결을 위한 앱 코드 수정이 필요하지 않다.
- 기존 검증 이후 소스가 바뀌지 않았거나 지금 다시 검증할 수 있다.

### 구현 및 복구 경로

다음 중 하나라도 해당하면 프로젝트를 먼저 점검하고 수정한다.

- 새 앱을 만들거나 기존 기능을 변경한다.
- 실행 명령, PORT, 환경변수 또는 Dockerfile 문제가 있다.
- 배포 전 검증이 실패한다.
- build, run 또는 health 단계에서 실패한다.
- 데이터 저장, 파일 업로드나 외부 서비스 연결이 필요하다.

중요한 제품 요구가 빠져 있고 안전하게 추론할 수 없을 때만 질문한다. 한 번에 최대 세 가지를 묻고, 나머지는 합리적인 기본값으로 진행한다.

## 전체 작업 흐름

### 1. 요청한 앱을 완성한다

- 새 앱을 만들거나 화면과 기능을 크게 바꾸는 요청이면 [앱 구현과 미리보기](references/app-building.md)를 읽는다.
- 현재 프로젝트에서 필요한 파일만 먼저 확인한다. 관련 없는 폴더를 광범위하게 읽지 않는다.
- 기존 실행 방식과 의존성을 함부로 교체하지 않는다.
- 앱의 주요 기능, 오류 상태, 모바일 사용성과 접근성을 요청 범위에 맞게 구현한다.
- 장식용 기능, 불필요한 상태 관리와 요청하지 않은 외부 서비스를 추가하지 않는다.
- 앱에 자체 로그인이 필요하면 플랫폼 로그인과 섞지 않고 앱 기능으로 구현한다.

Node 서버는 `process.env.PORT`를 사용하고 외부에서 접근할 수 있게 listen해야 한다. 루트에 `index.html`만 있는 정적 사이트는 별도 서버 코드 없이 배포할 수 있다. 자체 Dockerfile은 `package.json` 없이도 사용할 수 있다. 구체적인 실행 계약이나 Dockerfile 판단이 필요하면 [배포 계약과 복구](references/deployment-contract.md)를 읽는다.

### 2. 설정과 영속 자원 요구를 정리한다

- 공개해도 되는 일반 설정은 `env`로 분류한다.
- API 키, 비밀번호와 접속 Credential은 `secrets`로 분류한다.
- 비밀값 원문을 소스, 답변, 로그나 검증 요청에 넣지 않는다.
- 검증에는 비밀값 원문 대신 `secretKeys`만 전달한다.
- 앱이 데이터 저장이나 파일 업로드를 요구하면 [DB와 파일 Storage](references/resource-bindings.md)를 읽는다.
- 설정을 추가, 변경하거나 삭제할 때는 [설정과 비밀값](references/configuration-and-secrets.md)을 읽는다.

### 2.0 비밀값을 안전한 로컬 설정으로 정리한다

`validate_project`가 `hardcoded-secret`을 반환하거나 사용자가 비밀번호, API 키와 token을 소스에 직접 넣었다면 원문을 답변에 반복하지 않는다. 발견 위치, 노출 위험과 최소 변경만 설명하고 다음 문장처럼 사용자 동의를 받는다.

> 코드에 직접 저장된 비밀값을 발견했습니다. 코드는 환경변수를 사용하도록 바꾸고 현재 값은 Git에서 제외한 로컬 설정으로 옮겨 배포할까요?

사용자가 동의하면 다음 순서로 처리한다.

1. 소스의 고정값을 `process.env.<KEY>` 참조로 바꾼다.
2. 실제 값은 프로젝트 루트의 `.env.local`에 저장한다. 기존 파일이 있으면 다른 키를 보존한다.
3. `.gitignore`가 `.env`와 실제 `.env.*` 값 파일을 제외하고 예시 파일은 허용하는지 확인한다.
4. 필요한 경우 키 이름만 있는 `.env.example`을 자동으로 만든다. 사용자에게 이 파일을 직접 관리하라고 요구하지 않는다.
5. `validate_project`에는 `localEnv.file`과 사용자가 승인한 `envKeys` 또는 `secretKeys`만 전달한다.
6. 소스를 수정했으므로 반드시 다시 검증한다.
7. `deploy_project`에도 같은 `localEnv` 선택을 전달한다. MCP가 값을 로컬에서 직접 읽으며 Agent 응답과 도구 결과에는 반환하지 않는다.

새로 필요한 사용자 지정 비밀번호는 Agent 세션에서 입력받을 수 있다. 입력 목적과 사용 위치를 먼저 설명하고, 받은 값을 답변에서 확인 목적으로 되읽지 않는다. `.env.local`에 저장한 뒤에는 후속 도구 인자에 원문을 반복하지 않고 `localEnv` 선택을 사용한다.

하드코딩 제거 동의와 새 값 입력을 한 문장으로 함께 요청할 수 있다. 사용자가
설명을 확인한 뒤 새 값을 입력하면 해당 최소 변경에 동의한 것으로 보고 진행한다.
앱이 이미 정한 형식 규칙만 확인하며 값을 임의로 보정하거나 대신 생성하지 않는다.
현재 파일에서 제거해도 기존 Git 이력은 자동으로 재작성하지 않는다. 외부에 공개된
Credential의 교체나 이력 정리는 별도 승인을 받는다.

로컬 env 파일의 모든 키를 자동 전송하지 않는다. 현재 앱이 실제로 사용하고 사용자가 이동 또는 배포를 승인한 키만 `envKeys` 또는 `secretKeys`에 넣는다. 일반 문자열을 비밀값으로 확신할 수 없으면 임의로 수정하지 않고 짧게 설명한다.

예시:

```json
{
  "localEnv": {
    "file": ".env.local",
    "secretKeys": ["ADMIN_PASSWORD"]
  }
}
```

### 2.1 기존 로컬 영속 스택을 진단한다

`validate_project` 응답의 `transitions`가 비어 있지 않으면 일반 배포 흐름을 잠시 멈춘다. 이 진단은 읽기 전용이며 이 시점에는 소스, SQLite 파일, 로컬 PostgreSQL과 업로드 파일을 변경하지 않는다.

각 전환 계획에서 다음 내용을 쉬운 말로 정리한다.

- 현재 구성과 근거가 된 파일
- 제안 대상과 유지 가능한 대안
- 기존 데이터 존재 여부
- 필요한 코드 변경과 데이터 작업
- 위험도와 비가역 지점
- 배포 후 확인할 기능과 데이터

사용자가 처음부터 배포를 요청했더라도 영속 스택 전환 승인으로 간주하지 않는다. 위 내용을 설명한 뒤 반드시 "배포에 맞게 영속 스택을 전환하고 배포할까요?"라고 별도로 확인한다.

승인 전에는 다음 작업을 하지 않는다.

- source 파일, schema, migration과 설정 변경
- SQLite 파일 복사 또는 export
- Docker Compose PostgreSQL의 dump 또는 종료
- 로컬 업로드 파일 이동 또는 전송
- 외부 관리형 DB와 Storage의 export, import와 Credential 변경

사용자가 전환을 승인하면 다음 순서로 진행한다.

1. 변경 대상 파일과 현재 Git 상태를 기록한다.
2. SQLite는 `preview_sqlite_transition`, 로컬 파일은 `preview_local_files_transition`으로 읽기 전용 미리보기를 만들고 checksum을 기록한다.
3. `dataOperations`의 preview에 따라 대상, schema, 예상 건수, 실행 명령과 검증 절차를 보여준다.
4. 기존 데이터가 있으면 실제 import 명령을 실행하기 전에 데이터 이전 승인을 한 번 더 받는다.
5. 승인한 codeChanges만 적용하고 로컬 테스트를 실행한다.
6. 변경한 소스를 배포해 빈 PostgreSQL 또는 Storage binding을 먼저 준비한다.
7. SQLite는 `migrate_sqlite_data`, 로컬 파일은 `migrate_local_files`를 `approved: true`로 호출한다. 도구가 `.paas-backups/`에 원본 백업을 만든 뒤 승인한 데이터만 새 대상으로 이전한다.
8. 원본과 백업은 수정하지 않는다. 실패하면 도구가 대상 transaction 또는 이번에 올린 파일만 정리한다.
9. 배포 앱에서 CRUD와 파일 다운로드를 검증한다.
10. 같은 이름으로 다시 배포한 뒤 데이터와 파일이 유지되는지 확인한다.

소스 변경 뒤에는 `validate_project`를 다시 호출하고 `conversion-required`가 사라진 정확한 소스만 배포한다. 데이터 이전 도구는 이미 생성된 Deployment의 빈 대상에만 사용한다.

재검증에서 `conversion-required` 또는 `manual-required`가 남으면 배포하지 않는다. `choice-required`는 사용자의 유지 또는 이전 선택을 기록한 뒤 진행한다. 지원하지 않는 구성은 추측으로 변환하지 않고 `manualSteps`와 수동 절차를 안내한다.

SQLite, Compose PostgreSQL, 로컬 파일과 외부 관리형 자원의 구체적인 전환 기준은 [DB와 파일 Storage](references/resource-bindings.md)를 따른다.

### 3. 완성된 소스를 검증한다

소스 변경을 마친 뒤 `validate_project`를 호출한다.

- 로컬 작업물은 현재 프로젝트의 절대 경로를 사용한다.
- public Git 저장소는 HTTPS 주소를 사용할 수 있다.
- `deployable`이 `false`면 `issues`의 `path`, `message`, `fix`를 읽고 코드를 수정한다.
- `severity: error`를 모두 해결한 뒤 다시 검증한다.
- 소스를 한 줄이라도 수정했으면 이전 검증 결과를 재사용하지 않고 다시 검증한다.
- warning은 배포를 막지 않는다. 보안, 데이터 손실 또는 주요 기능에 영향을 주는 경우에만 사용자에게 알린다.
- 검증을 우회하거나 분석 결과에서 요청 기능을 제거해 억지로 통과시키지 않는다.

검증이 성공한 뒤에는 배포 전까지 제품 소스를 계획적으로 더 수정하지 않는다. 수정이 필요해지면 다시 검증한다.

### 4. 검증한 소스를 배포한다

`deploy_project`에 검증할 때 사용한 것과 같은 소스를 전달한다.

- 커밋하지 않은 로컬 변경이 있으면 로컬 경로를 사용한다.
- Git 주소를 사용하면 원격 저장소에 올라간 내용만 배포된다.
- 기존 앱을 갱신할 때는 기존 배포 이름을 재사용한다.
- 이름을 생략하면 플러그인이 프로젝트 이름에서 안전한 값을 만든다.
- CPU와 메모리는 사용자가 특별히 요구하거나 기본값으로 부족한 근거가 있을 때만 지정한다.
- 일반 설정은 `env`, 비밀값은 `secrets`로 전달한다.
- 로컬 env 파일로 정리한 값은 원문 `env` 또는 `secrets` 대신 `localEnv`의 승인한 키 목록으로 전달한다.
- 같은 비밀값을 답변이나 후속 도구 호출에 다시 표시하지 않는다.

배포 요청은 빌드, 실행과 healthcheck가 끝날 때까지 기다린다. 성공 응답의 `url`을 사용하고 주소를 이름으로 직접 조립하지 않는다.

### 5. 결과를 전달한다

성공하면 다음 순서로 짧게 답한다.

1. 앱이 준비됐다는 결론
2. 정확한 접속 URL
3. 사용자가 지금 할 수 있는 주요 기능
4. 꼭 알아야 하는 제한이 있을 때만 한 줄 설명

기본 답변에는 내부 ID, revision 번호, 이미지 이름, host port, 토큰, 명령어와 임시 경로를 넣지 않는다.

예시:

> 앱을 배포했습니다: https://example.example.com
>
> 이제 할 일을 추가하고 완료 상태를 관리할 수 있습니다.

## 실패 처리와 재시도

- 실패 응답의 `stage`를 먼저 확인한다.
- build, run 또는 health 실패는 `deployment_logs`로 원인을 확인하고 수정한 뒤 다시 검증한다.
- 원인을 확인하지 않은 동일 배포 반복은 하지 않는다.
- queue 실패의 `details.retryable`을 확인한다. `true`면 짧게 기다린 뒤 한 번만
  다시 시도한다. `false`인 `disk-capacity`와 `port-capacity`는 반복하지 않고
  기존 앱이 계속 제공된다는 점과 운영자에게 필요한 용량 조치를 설명한다.
- 인증, 권한, 사용량 제한과 접근 오류는 임의로 우회하지 않는다.
- 배포 이름 충돌 외에는 이름을 추측해서 바꾸지 않는다. 기존 URL이 불필요하게 달라질 수 있다.
- 새 revision이 실패해도 이전 revision은 계속 서비스된다. 이전 앱을 중지하거나 삭제하지 않는다.

단계별 원인과 조치 기준은 [배포 계약과 복구](references/deployment-contract.md)를 따른다.

## 연결과 인증

연결이나 인증이 의심되면 `paas_whoami`를 한 번 호출한다.

- Credential이 없으면 `start_paas_login`으로 로그인 주소와 코드를 받은 뒤 사용자가 승인하면 `complete_paas_login`을 실행한다.
- `PAAS_TOKEN`은 이전 운영 및 CI용 service Credential 호환 경계이며 개인 기기 로그인과 구분한다.
- 401이면 Credential이 잘못됐거나 폐기된 것이다. 재발급이 필요하다고 설명한다.
- 연결 실패면 PaaS 주소나 서비스 상태를 확인해야 한다.
- 토큰 원문을 사용자에게 되읽거나 로그에 남기지 않는다.
- Workspace를 생략하면 개인 Workspace를 사용한다.
- Team Workspace에서 작업할 때는 모든 관련 도구에 같은 `workspace` ID 또는 slug를 전달한다.
- 대상이 불분명하면 `paas_whoami`로 접근 가능한 Workspace를 확인하고 임의로 고르지 않는다.

## 기존 배포 관리

- `list_deployments`: 사용자가 관리할 수 있는 앱 목록과 상태
- `deployment_status`: 현재 상태와 접속 URL
- `stop_deployment`: 실행 중지. 배포 기록과 영속 자원은 유지
- `delete_deployment`: 배포 삭제. 영속 자원 보존 또는 삭제 정책을 반드시 선택
- `deployment_logs`: build 또는 runtime 문제 확인
- `deployment_config`: 일반 설정과 비밀값 키 이름 확인
- `set_deployment_config`: 설정 추가, 변경과 삭제
- `paas_whoami`: 사용자, Workspace와 연결 상태 확인

다른 Workspace의 배포는 존재 여부를 추측하지 않는다. 404면 권한이 없거나 대상이 없는 것으로만 설명한다.

## 현재 플랫폼 범위

- 로컬 프로젝트와 public Git 저장소를 배포할 수 있다.
- 정적 사이트, 일반 Node 앱, 주요 Node 웹 프레임워크와 자체 Dockerfile을 지원한다.
- 일반 환경변수와 암호화된 비밀값을 지원한다.
- 개인 및 Team Workspace별 배포와 공동 관리를 지원한다.
- PostgreSQL과 파일 Storage 요구를 감지해 배포별 자원과 Credential을 자동 연결한다.
- SQLite, Compose PostgreSQL, 로컬 파일과 외부 관리형 자원을 읽기 전용으로 진단하고 승인 기반 전환 계획을 제공한다.
- private Git 저장소 인증은 아직 지원하지 않는다. 커밋하지 않은 변경이나 private 저장소는 로컬 경로로 배포한다.
- 배포 관리 권한과 배포 앱 내부 사용자 인증은 서로 별개다.
