# 앱 구현과 미리보기

## 구현 경로 선택

다음 조건을 모두 만족하면 한 번에 완성하는 경로를 사용한다.

- 새 앱이거나 비어 있는 프로젝트다.
- 한 화면이나 한 route로 핵심 요구를 충족할 수 있다.
- DB, 파일 업로드, 앱 자체 인증과 외부 데이터 연결이 필요하지 않다.
- 사용자가 별도 브라우저 검사를 요청하지 않았다.

기존 앱 수정, 여러 route, 데이터 저장, 업로드, 인증, 외부 데이터나 브라우저 검사가 포함되면 기능 중심 경로를 사용한다. 이때도 필요한 기능만 추가하고 기존 구조를 교체하지 않는다.

## 새 프로젝트 시작

- 프로젝트에 이미 프레임워크, package manager, lockfile과 실행 구조가 있으면 그대로 사용한다.
- 비어 있는 프로젝트라면 요구를 만족하는 가장 작은 일반적인 구조로 바로 시작한다.
- 설치가 진행되는 동안 독립적으로 작성할 수 있는 첫 화면과 콘텐츠를 먼저 구현할 수 있다.
- 초기화 도구를 중복 실행하거나 작동하는 구조를 다른 starter로 덮어쓰지 않는다.

## 첫 의미 있는 미리보기

클라이언트가 사용자에게 로컬 미리보기를 보여주는 기능을 제공하고 현재 작업이 화면 중심이라면, 완성 전에도 다음 조건을 만족하는 첫 버전을 한 번 보여줄 수 있다.

- 요청한 앱임을 바로 알아볼 수 있는 실제 제목과 대표 콘텐츠가 있다.
- 핵심 화면 구조와 주요 동작이 보인다.
- 빈 화면, 범용 skeleton과 loading 화면만 보여주지 않는다.
- 개발 서버가 오류 없이 compile되고 해당 route가 정상 응답한다.

첫 미리보기는 작은 완성 단위다. 보조 화면, 전체 데이터 모델, 세부 반응형 조정과 장식은 이후에 완성한다. 미리보기 전에는 계획된 소스 수정을 잠시 멈추고 blocking 오류만 해결한다. 같은 클라이언트에서 화면을 다시 열 수 있으면 기존 탭이나 미리보기 영역을 재사용한다.

미리보기 기능이 없거나 백그라운드 작업이면 이 단계를 건너뛴다. 미리보기 실패는 build와 배포를 막지 않는다.

## 제품 화면 구현

- 첫 화면은 범용 dashboard 장식보다 사용자가 요청한 핵심 작업을 중심으로 구성한다.
- 임시 문구와 starter metadata를 실제 제품 제목, 설명과 콘텐츠로 바꾼다.
- 현실적인 예시 데이터를 사용하되 실제 사용자 데이터인 것처럼 속이지 않는다.
- 필요한 상호작용, 모바일 동작, keyboard 사용성과 접근 가능한 label을 구현한다.
- 요청하지 않은 기능과 불필요한 client state를 추가하지 않는다.
- 브라우저 저장소는 기기 안에서만 유지돼도 되는 설정이나 명시적인 로컬 상태에만 사용한다.

## 이미지와 시각 자료

- 이미지가 필요하지 않으면 typography, 색상, 배치, CSS와 기존 icon 체계를 우선한다.
- 실제 이미지가 제품 이해에 중요하면 사용 권한을 확인할 수 있는 적절한 이미지를 찾는다.
- 기존 이미지로 요구를 충족할 수 없고 고유한 시각 자료가 중요할 때만 이미지 생성을 사용한다.
- 장식만을 위한 임의의 SVG 그림이나 생성 이미지를 과도하게 추가하지 않는다.

## 최종 검증

- 요청한 기능을 모두 구현한 뒤 프로젝트의 표준 build를 실행한다.
- build가 compile을 포함하지 않을 때만 별도 typecheck나 lint가 필요한지 확인한다.
- 실제 오류만 수정하고 소스가 바뀌면 build와 `validate_project`를 다시 실행한다.
- 사용자가 요청하지 않았다면 screenshot, DOM 조사, 반복 클릭과 여러 화면 크기 비교를 배포 조건으로 만들지 않는다.
- build와 배포 전 검증이 성공하면 불필요한 polish 단계를 추가하지 않고 배포한다.
