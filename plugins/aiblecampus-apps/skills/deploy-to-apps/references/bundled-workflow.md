# 에이블캠퍼스 Apps 배포

사용자가 명시적으로 배포를 요청한 웹앱을 검증하고 접속 가능한 상태로 만든다. 소스 패키징, 컨테이너, revision과 내부 API는 작업 수단이지 사용자에게 설명할 기본 내용이 아니다.

플러그인 설치나 복구가 필요하면 [manage-apps-plugin](../manage-apps-plugin/SKILL.md)을 따른다. AI 요청과 응답 기능 구현에는 [build-ai-feature](../build-ai-feature/SKILL.md)를 사용한다.

## 배포 실행 조건

- "앱 만들어줘", "고쳐줘", "테스트해줘", "미리보기 보여줘"는 구현과 로컬 검증까지만 한다. 배포가 없다고 개발을 멈추거나 배포 승인을 거듭 묻지 않는다.
- "배포 가능한지 확인해줘", "배포 상태 확인", "로그 봐줘"는 검증이나 조회만 한다. 환경변수와 비밀값 설정 요청도 그 설정 변경 범위에 한정하며 새 버전 배포나 별도 재시작으로 확장하지 않는다. 추가 배포가 필요하면 필요성을 설명한다.
- 기존 배포 URL, 설치된 플러그인, 성공한 검증, `.aiblecampus-deploy.json`과 과거 완료된 배포 요청은 이후 개발 작업의 배포 허가가 아니다. 인계 기록은 대상과 설정을 확인하는 용도로만 쓴다.
- 진행 중인 "만들어서 배포해줘" 작업에서는 필요한 구현, 검증, 오류 수정과 재시도를 같은 요청 안에서 이어간다. 이미 완료된 배포 이후의 새로운 수정 요청에는 별도의 명시적인 배포 요청이 필요하다. 사용자가 배포를 취소하거나 이번에는 배포하지 말라고 하면 중단한다.
- `deploy_project`뿐 아니라 CLI, API, CI 실행 등 다른 경로로도 이 조건을 우회하지 않는다. 배포를 유발하는 push나 자동화 실행도 동일하게 적용한다.

## 시작하기

"에이블캠퍼스에 배포해줘" 한 줄이면 충분하다. 경로와 이름은 프로젝트에서 확인한다. 작업 공간은 현재 요청과 `.aiblecampus-deploy.json` 인계 기록을 먼저 확인한다. 대상이 없으면 허브 "배포 방법" 창과 같은 말로 "개인 산출물 배포"와 "조 산출물 배포(4조)" 중 무엇인지 한 번 묻는다. 조 이름은 `apps_whoami`의 실제 소속 조를 쓰고 조가 없으면 개인 산출물 배포만 있다고 알린다. 조 대상이 확인되지 않는다고 개인 공간으로 배포하지 않는다.

### 이럴 때만 되묻는다

- 열려 있는 프로젝트가 없거나 배포할 대상이 둘 이상이라 무엇을 올릴지 정할 수 없다.
- 현재 요청과 프로젝트의 인계 기록에도 배포 대상이 없다. "개인 산출물 배포"와 "조 산출물 배포(조 이름)" 중 무엇인지 한 번 확인하고 `apps_whoami`로 해당 UUID와 권한을 확인한다.
- 사용자가 "같은 이름으로 새 앱"을 요청했고 같은 이름 앱이 이미 있다. "기존 앱을 새 버전으로 갱신(주소 유지)"과 "다른 이름의 새 앱으로 배포" 중 고르게 한다. 다른 폴더로 복사해 우회하지 않는다. 새 앱을 고르면 다른 이름을 받아 배포하고, 서버가 같은 공간의 같은 표시 이름 뒤에 번호를 붙였으면(응답 `displayName`) 그 이름을 알린다.
- 앱이 아직 없어서 무엇을 만들지 정해야 하고 안전하게 추론할 수 없다.

## 개인 앱과 조 앱

- 조 작업 공간에는 앱을 하나만 둔다. 조 배포 요청이면 `apps_whoami`로 조와 배포 권한을 확인하고 그 workspace의 앱 목록을 조회한다. 조 앱이 있으면 이름을 다시 묻지 않고 그 앱의 이름을 재사용해 주소, 저장소와 데이터를 유지한 채 갱신한다.
- 조 앱이 아직 없으면 현재 프로젝트에서 이름을 정해 첫 앱을 만든다. 다른 조로 추측하여 전환하지 않는다. 소속 조가 여러 개이고 요청이나 인계 기록으로 구분할 수 없을 때만 조를 확인한다.
- 조는 허브에서 운영진이 편성한다. 참가자는 여러 조에 배정될 수 있고 Apps와 갤러리는 같은 배정을 쓴다. 참가자에게 조 생성이나 참여 코드를 안내하지 않는다.

## 실행 경로 선택

### 빠른 배포 경로

다음 조건을 모두 만족하면 `validate_project`와 `deploy_project`만으로 진행한다.

- 현재 작업에 명시적인 배포 요청이 있다.
- 프로젝트 구현이 이미 끝났다.
- 사용자가 기능 변경을 요청하지 않았다.
- 필요한 일반 설정과 비밀값이 준비돼 있다.
- DB나 파일 Storage 연결을 위한 앱 코드 수정이 필요하지 않다.
- 기존 검증 이후 소스가 바뀌지 않았거나 지금 다시 검증할 수 있다.

### 구현 및 복구 경로

다음 중 하나라도 해당하면 프로젝트를 먼저 점검하고 수정한다.

- 새 앱을 만들거나 기존 기능을 변경한다.
- 실행 명령, PORT, 환경변수 또는 Dockerfile 문제가 있다.
- 배포 전 검증이 실패한다.
- build, run 또는 health 단계에서 실패한다.
- 데이터 저장, 파일 업로드나 외부 서비스 연결이 필요하다.

브라우저 조작, screenshot과 시각 검사는 사용자가 요청했거나 기능 확인에 꼭 필요한 경우에만 한다.

## 진행 안내

진행 상황은 사용자가 이해할 수 있는 단계로 짧게 설명한다.

- 준비: "요청한 기능을 완성하고 있습니다."
- 검증: "완성된 앱이 정상적으로 실행되는지 확인하고 있습니다."
- 배포: "앱이 준비됐습니다. 지금 접속할 수 있게 배포하고 있습니다."

한 단계가 60초보다 오래 걸릴 때만 짧은 추가 진행 상황을 보낸다. 소스 압축과 업로드 방식, 명령어와 package manager 내부 처리, 토큰과 내부 API 주소, 배포 ID, revision ID, 컨테이너와 대기열 수치는 사용자가 묻거나 직접 조치해야 할 때만 설명한다. 복구 가능한 기술 오류는 먼저 직접 해결하고, 해결할 수 없을 때만 원인과 필요한 다음 행동을 쉬운 말로 설명한다.

## 1. 앱 완성

- 새 앱을 만들거나 화면과 기능을 크게 바꾸는 요청이면 [앱 구현과 미리보기](references/app-building.md)를 읽는다. 실행 계약이나 Dockerfile 판단이 필요하면 [배포 계약과 복구](references/deployment-contract.md)를 읽는다.
- 앱에 자체 로그인이 필요하면 플랫폼 로그인과 섞지 않고 앱 기능으로 구현한다.
- 현재 프로젝트 밖에서 `.npmrc`, env 파일, 개인 token이나 Credential을 검색하지 않는다.

## 2. 설정과 비밀값

- 배포할 때 소스 루트의 `.env.production.local`, `.env.local`, `.env.production`, `.env` 값은 앱 비밀값으로 자동 등록된다(앞 파일 우선). 배포 요청의 `env`, `secrets`, `localEnv`와 이미 저장된 설정이 먼저이고 파일은 없는 키만 더하며, `PORT`, `NODE_ENV`, `DATABASE_URL`, `APPS_` 접두 키는 등록하지 않는다. 정적 앱은 `.env` 같은 점 파일을 브라우저에 주지 않는다(404).
- `.env`와 `.env.*` 값 파일(`.env.apps-ai` 포함)도 소스 압축에 포함된다. 교육 설계상 의도한 동작이다. env 파일 포함만으로 배포를 중단하지 않고, 사용자가 소스 포함을 선택하면 파일 제외나 설정 이전을 강제하지 않는다. 참가자가 물으면 의도된 동작이라고 답한다.
- 앱이 데이터 저장이나 파일 업로드를 요구하면 [DB와 파일 Storage](references/resource-bindings.md)를 읽는다.

### 하드코딩 비밀값 정리

`hardcoded-secret`은 배포를 막지 않는 경고다. 사용자가 소스 포함을 선택했다면 그 선택을 유지하고, 설정 이전을 원할 때만 다음 절차를 따른다. 원문은 답변에 반복하지 않고 발견 위치, 노출 위험과 최소 변경만 설명한 뒤 다음 문장처럼 동의를 받는다.

> 코드에 직접 저장된 비밀값을 발견했습니다. 코드는 환경변수를 사용하도록 바꾸고 현재 값은 Git에서 제외한 로컬 설정으로 옮겨 배포할까요?

동의하면 다음 순서로 처리한다.

1. 소스의 고정값을 `process.env.<KEY>` 참조로 바꾼다.
2. 실제 값은 프로젝트 루트의 `.env.local`에 저장한다. 기존 파일이 있으면 다른 키를 보존한다.
3. `.gitignore`가 `.env`와 실제 `.env.*` 값 파일을 제외하고 예시 파일은 허용하는지 확인한다.
4. 필요하면 키 이름만 있는 `.env.example`을 만든다. 사용자에게 이 파일을 직접 관리하라고 요구하지 않는다.
5. 소스를 고쳤으므로 `validate_project`로 다시 검증하고, 검증과 배포에 같은 `localEnv` 선택을 넣는다.

새로 필요한 사용자 지정 비밀번호는 Agent 세션에서 입력받을 수 있다. 입력 목적과 사용 위치를 먼저 설명하고, 받은 값을 되읽지 않고 `.env.local`에 저장한 뒤 후속 도구 인자에는 `localEnv` 선택을 쓴다. 하드코딩 제거 동의와 새 값 입력을 한 문장으로 함께 요청할 수 있고, 사용자가 설명을 확인한 뒤 새 값을 입력하면 그 최소 변경에 동의한 것으로 본다. 앱이 정한 형식 규칙만 확인하며 값을 임의로 보정하거나 대신 생성하지 않는다. 사용자에게 `.env` 사용법을 먼저 가르치지 않는다.

현재 파일에서 제거해도 기존 Git 이력은 자동으로 재작성하지 않는다. 외부에 공개된 Credential의 교체나 이력 정리는 별도 승인을 받는다. 일반 문자열을 비밀값으로 확신할 수 없으면 임의로 고치지 않고 짧게 설명한다.

## 2.1 영속 스택 전환

`validate_project` 응답의 `transitions`가 비어 있지 않으면 일반 배포 흐름을 잠시 멈춘다. 이 진단은 읽기 전용이며 이 시점에는 소스, SQLite 파일, 로컬 PostgreSQL과 업로드 파일을 변경하지 않는다.

각 전환 계획에서 다음 내용을 쉬운 말로 정리한다.

- 현재 구성과 근거가 된 파일
- 제안 대상과 유지 가능한 대안
- 기존 데이터 존재 여부
- 필요한 코드 변경과 데이터 작업
- 위험도와 비가역 지점
- 배포 후 확인할 기능과 데이터

사용자가 처음부터 배포를 요청했더라도 영속 스택 전환 승인으로 간주하지 않는다. 위 내용을 설명한 뒤 반드시 "배포에 맞게 영속 스택을 전환하고 배포할까요?"라고 별도로 확인한다.

승인 전에는 다음 작업을 하지 않는다.

- source 파일, schema, migration과 설정 변경
- SQLite 파일 복사 또는 export
- Docker Compose PostgreSQL의 dump 또는 종료
- 로컬 업로드 파일 이동 또는 전송
- 외부 관리형 DB와 Storage의 export, import와 Credential 변경

사용자가 전환을 승인하면 다음 순서로 진행한다.

1. 변경 대상 파일과 현재 Git 상태를 기록한다.
2. SQLite는 `preview_sqlite_transition`, 로컬 파일은 `preview_local_files_transition`으로 읽기 전용 미리보기를 만들고 checksum을 기록한다.
3. `dataOperations`의 preview에 따라 대상, schema, 예상 건수, 실행 명령과 검증 절차를 보여준다.
4. 기존 데이터가 있으면 실제 import 명령을 실행하기 전에 데이터 이전 승인을 한 번 더 받는다.
5. 승인한 codeChanges만 적용하고 로컬 테스트를 실행한다.
6. 변경한 소스를 배포해 빈 PostgreSQL 또는 Storage binding을 먼저 준비한다.
7. SQLite는 `migrate_sqlite_data`, 로컬 파일은 `migrate_local_files`를 `approved: true`로 호출한다. 도구가 `.apps-backups/`에 원본 백업을 만든 뒤 승인한 데이터만 새 대상으로 이전한다.
8. 원본과 백업은 수정하지 않는다. 실패하면 도구가 대상 transaction 또는 이번에 올린 파일만 정리한다.
9. 배포 앱에서 CRUD와 파일 다운로드를 검증한다.
10. 같은 이름으로 다시 배포한 뒤 데이터와 파일이 유지되는지 확인한다.

소스 변경 뒤에는 `validate_project`를 다시 호출하고 `conversion-required`가 사라진 정확한 소스만 배포한다. 재검증에서 `conversion-required` 또는 `manual-required`가 남으면 배포하지 않는다. `choice-required`는 사용자의 유지 또는 이전 선택을 기록한 뒤 진행한다. 지원하지 않는 구성은 추측으로 변환하지 않고 `manualSteps`와 수동 절차를 안내한다. 구체적인 전환 기준은 [DB와 파일 Storage](references/resource-bindings.md)를 따른다.

## 3. 검증

패키징과 빌드가 필요한 앱은 [배포 계약과 복구](references/deployment-contract.md)의 패키징 기준을 확인한 뒤 `validate_project`를 호출한다.

## 4. 조 앱 소스 통합

조 앱을 수정하기 전에 `checkout_app_source`로 최신 기본 브랜치를 새 폴더에 받는다. 기존 작업 폴더를 덮어쓰지 않는다. 작업 시작 당시 `.apps-source.json`의 커밋을 `checkout_app_source`의 `commit`으로 지정하면 기준 소스도 별도 폴더에 받을 수 있다. 기준 소스, 현재 작업과 최신 소스를 비교해 자신의 변경만 반영하고 기능과 빌드를 검증한다. 같은 부분을 수정했더라도 양쪽 의도를 유지할 수 있으면 직접 통합한다. 서로 양립할 수 없는 요구사항이거나 자신의 변경 범위를 확정할 수 없으면 충돌 위치, 각 변경의 목적과 선택지를 사용자에게 설명하고 결정을 받은 뒤 통합한다.

`source-conflict`가 반환되면 기존 배포 요청이 유효한 한 사용자에게 재시도를 맡기거나 재승인을 요청하지 않는다. 응답의 recovery 절차대로 최신 소스를 받아 자신의 변경을 통합하고 검증한 뒤 같은 앱 이름과 workspace로 재배포한다. 연속 3회 충돌하면 동시 수정 상황과 진행 결과를 보고한다.

## 5. 결과 전달

성공하면 다음 순서로 짧게 답한다.

1. 앱이 준비됐다는 결론과 앱 이름
2. 정확한 접속 URL
3. 사용자가 지금 할 수 있는 주요 기능
4. 꼭 알아야 하는 제한이 있을 때만 한 줄 설명

기본 답변에는 내부 ID, revision 번호, 이미지 이름, host port, 토큰, 명령어와 임시 경로를 넣지 않는다.

> 앱을 배포했습니다: https://example.example.com
>
> 이제 할 일을 추가하고 완료 상태를 관리할 수 있습니다.

## 실패 처리와 재시도

재배포와 재시도는 아직 진행 중인 명시적인 배포 요청 안에서만 수행한다. 별도의 "실패 원인을 찾아서 고쳐줘" 요청은 진단, 수정과 검증까지만 수행하며 자동으로 재배포하지 않는다.

- 실패 응답의 `stage`를 먼저 확인한다. build, run 또는 health 실패는 `deployment_logs`로 원인을 확인하고 수정한 뒤 다시 검증한다.
- 원인을 확인하지 않은 동일 배포 반복은 하지 않는다.
- `deploy_project`가 연결 오류, 제한 시간 초과 또는 응답 없음으로 끝나면 같은 이름으로 `deployment_status`를 먼저 호출한다.
- `latestRevision.status`가 queued, building 또는 healthcheck면 새 Revision을 만들지 않고 기존 작업이 끝날 때까지 상태와 로그를 조회한다.
- `latestRevision.status`가 running이면 기존 요청이 성공한 것으로 보고 응답의 URL을 사용한다.
- `latestRevision.status`가 failed면 그 항목의 `error`와 해당 Revision 로그를 확인해 원인을 고치고 다시 검증한 뒤에만 재배포한다. `currentRevision`이 따로 있으면 이전 정상 Revision이 계속 서비스되고 있다는 뜻이다.
- 대상이 두 번 연속 404이고 진행 중인 Revision이 없음을 확인한 경우에만 같은 요청을 한 번 다시 보낼 수 있다.
- private package registry가 401 또는 403을 반환하면 사용자 홈이나 다른 프로젝트에서 token과 `.npmrc`를 찾지 않는다. 개인 Credential을 소스나 배포 비밀값으로 복사하지 않는다. 공개 의존성으로 교체, 조직이 관리하는 빌드 Credential 지원 또는 패키지 공개 중 가능한 선택지를 설명하고 사용자 결정을 기다린다.

단계별 원인과 조치 기준은 [배포 계약과 복구](references/deployment-contract.md)를 따른다.

## 도움받을 곳과 플랫폼 범위

- 허브: 참가자는 내 앱에서 개인 앱과 조 앱의 상태, 배포 기록, 로그와 설정을 보고 진단과 갤러리 제출도 한다. 운영진은 교육, 참가자, 조 편성, 앱용 AI 설정과 갤러리를 관리한다. 참가자에게 운영 화면 접근이나 직접 조 생성을 요구하지 않는다.
- 진단: 교육 담당자가 안내한 허브 진단 화면에서 한다. Apps 배포 권한과 별개이며 배포를 위해 진단 설정을 바꾸지 않는다.
- 갤러리 제출물의 파일과 발표 PDF는 허브 갤러리 제출 페이지에서 올린다. Apps에서 PDF를 올리지 않는다.
- 로컬 프로젝트와 public Git 저장소를 배포할 수 있다. private Git 저장소 인증은 아직 지원하지 않는다.
- 정적 사이트, 일반 Node 앱, 주요 Node 웹 프레임워크와 자체 Dockerfile을 지원한다.
- 일반 환경변수와 암호화된 비밀값, 개인과 조 공간별 배포를 지원한다.
- 앱이 PostgreSQL이나 파일 Storage를 쓰면 배포별 자원을 자동으로 연결한다. SQLite, Compose PostgreSQL, 로컬 파일과 외부 관리형 자원은 읽기 전용으로 진단하고 승인 기반 전환 계획을 낸다.
- 배포 관리 권한과 배포 앱 내부 사용자 인증은 서로 별개다.

## 디자인과 설명 스킬 연결

- 요청에 화면 제작이나 UI 개선이 포함되면 `../frontend-design/SKILL.md`를 읽고 해당 작업에 적용한다.
- 복잡한 구조를 그림으로 쉽게 설명해 달라는 요청에는 `../eli5/SKILL.md`를 사용한다.
- 배포만 요청한 경우 화면을 다시 디자인하지 않는다. 일반 진행 보고에는 설명용 HTML을 만들지 않는다.
